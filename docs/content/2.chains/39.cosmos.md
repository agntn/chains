## Cosmos Hub address format

Cosmos Hub addresses use Bech32 with the original BIP-173 checksum, not Bech32m. The prefix is `cosmos`, so addresses start with `cosmos1`.

The validator checks the prefix, length cap, Bech32 alphabet, case and checksum. It also checks that the digits pack into whole bytes with zero padding. The decoded payload must be 20 or 32 bytes. It reports every broken rule at once.

All lowercase or all uppercase passes. Mixed case fails with `upper and lower case mixed, which Bech32 forbids`. A wrong last character fails with `the Bech32 checksum does not hold, so a character is wrong`.

It doesn't check whether the account exists. The address holds a hash, not the public key.

```ts
import { getChain } from "@agntn/chains";

const chain = getChain("atom");
chain.assertAddress("cosmos19rl4cm2hmr8afy4kldpxz3fka4jguq0auqdal4"); // returned unchanged
chain.caip2; // "cosmos:cosmoshub-4"
chain.bip44; // 118
```

`@agntn/keys` derives that address from the BIP39 test words at `m/44'/118'/0'/0/0`. Now the registry can say it's one. `decodeAddress` returns `{ kind: "account" }`.

Cosmos Hub has 6 decimals. One ATOM is 1,000,000 uatom.

## Cosmos payload lengths

Why 20 or 32 bytes? Both have jobs on the Hub.

A key account has a 20-byte payload. It's RIPEMD-160 of SHA-256 of the compressed secp256k1 public key.

Module accounts also use 20 bytes. They take the first 20 bytes of SHA-256 of the module name. For example, `fee_collector` becomes `cosmos17xpfvakm2amg962yls6f84z3kell8c5lserqta`. The name is the address, give or take a hash.

A 32-byte payload can represent a CosmWasm contract or another address derived under ADR-028. One contract address is `cosmos1cp28gxjul0eht3axzdd5npxq7zqzy07r9y36rnsdf3r4s2g6d8hszw5k3s`.

A 32-byte address is 65 characters long. That's at most 58 characters after `cosmos1`. A valid checksum doesn't excuse another payload length. A 21-byte payload fails with `decodes to 21 bytes, not 20 or 32`.

## Cosmos validator operators and other prefixes

Validator operator addresses use `cosmosvaloper1`, not `cosmos1`. The check refuses them on purpose. That's the right boundary: a validator operator address isn't an account address with a fancy title.

For example, `cosmosvaloper15gyzcp2kas2yntv9k3p0zm4k8y6e89ecmkeqee` fails with `does not start with cosmos1`.

Osmosis, Celestia and other Cosmos SDK chains share the key scheme, but use different prefixes. An `osmo1` or `celestia1` address isn't a Hub address, so it fails here.

The same 20 bytes can appear as `osmo1f7qvypfaee56km5rp8lvay4f0saq9xn4mz2srn` or `cosmos1f7qvypfaee56km5rp8lvay4f0saq9xn4neeq4p`. Same key, two chains. The prefix decides.

## Cosmos Hub chain ID

The Hub's chain ID is `cosmoshub-4`. Its CAIP-2 ID is `cosmos:cosmoshub-4`.

Cosmos CAIP-2 IDs use the chain ID. The `-4` suffix counts versions. Each restart from exported state got a new chain ID. Turning it off and on again, at chain scale. CAIP-2 treats each version as a separate chain.

## Cosmos address identification

What happens when you ask `identify` about a `cosmos1` address? It returns the Hub alone, with the key `cosmos`. A `cosmosvaloper1` address matches nothing.

## Cosmos Hub transaction hashes

A transaction hash is 64 hex digits. It's SHA-256 of the signed transaction bytes.

The node's REST and RPC interfaces print hashes uppercase. Either case passes. A `0x` prefix fails with `0x in front, which this chain's txids never carry`.

For example, `20D19763115DDE807A9502B61A6A2139E93B21040137BA7EC7E4FFF3659DD46E` identifies a MsgSend at height 34026315.

## Cosmos Hub chain spellings

Use `cosmos`, `Cosmos Hub`, `atom` or `cosmoshub` with `getChain`. Case doesn't matter.
