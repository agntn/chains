## Address format

A NEAR address is an account ID. Most of them read like domain names: `wrap.near`, `usdt.tether-token.near`. Only `near` can create `alice.near`, the way a registry owns its TLD.

The rules are those of `validate` in near-account-id-rs. Two to 64 characters. Lowercase `a-z` and `0-9`, with `-`, `_` or `.` between the parts. No separator at either end, never two in a row. Uppercase fails, because an account ID has exactly one spelling.

Some IDs carry a key instead of a name:

- NEAR-implicit: 64 hex digits, an Ed25519 public key.
- ETH-implicit: `0x` and 40 lowercase hex digits.
- Deterministic: `0s` and 40 hex digits.
- Universal: `0u` and 52 Crockford base32 digits.

They all pass through the same grammar. Nothing to decode.

And no checksum, anywhere. Mistype `wrap.near` as `wrap.neat` and you get a perfectly valid account. Maybe someone's.

```ts
import { getChain } from "@agntn/chains";

const chain = getChain("near");
chain.assertAddress("wrap.near"); // returned unchanged
chain.assertAddress("aurora"); // a top-level name, returned unchanged
chain.type; // "near"
chain.caip2; // "near:mainnet"
```

## Why identify is pickier

How loose is that grammar? `bc1qw508d6qejxtdg4y5r3zarvary0c5xw7kv8f3t4` is a valid account ID. So is every lowercase Bech32 address and every bare CashAddr.

So NEAR overrides `claimsAddress`. [Identify](/guide/identify) names it for IDs with a dot and for the four implicit forms. Bare words stay out. `assertAddress` still takes them, so `aurora` validates fine.

An ETH-implicit account shows up next to the EVM chains. Fair, it is the same 20 bytes.

## Transaction hashes

A 32-byte `CryptoHash` in base58, read the way `CryptoHash::from_str` reads it. Decode, count, done.

24 decimals, 10^24 yoctoNEAR per NEAR. Coin type 397. NEAR has no namespace in the ChainAgnostic registry, so `caip2` is `near:mainnet`, the id WalletConnect wallets pass around.

## Spellings

`near`, `NEAR Protocol`. The key is `near`, the rest resolve through `getChain`.
