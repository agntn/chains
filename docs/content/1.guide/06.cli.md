## Run it

```bash
pnpm add -g @agntn/chains
chains info matic
```

```text
Polygon PoS (polygon)
symbol: POL
decimals: 18
type: evm
chainId: 0x89
caip2: eip155:137
bip44: 60
explorer: https://polygonscan.com
rpc: https://polygon-bor-rpc.publicnode.com
```

That's the exact text `chains_lookup` hands a model. One answer for the terminal and the agent. Nobody learns two dialects of the same chain.

| Command | Description |
| --- | --- |
| `chains info <chain>` | Canonical metadata. `chains lookup` is the same command under the tool's name |
| `chains resolve <input>` | The canonical key for a name, symbol or alias, one line and nothing else |
| `chains validate <chain> <value>` | Check an address against one chain's format, or a transaction id with `--txid` |
| `chains txid <chain> <txid>` | Check a transaction id, without the flag |
| `chains identify <address>` | Which registered chains accept the address, grouped by family |
| `chains list [family]` | Every registered chain, or the ones in one family |
| `chains mcp` | Run the MCP server over stdio |

`--json` works everywhere except `mcp`. It prints the structured answer instead of the text. `info` gives the metadata, `validate` gives `{ chain, address, valid, reason, decoded }`. `identify` gives `{ address, matches, unchecked }`. `list` gives `{ chains, families }`, plus `family` when you name one.

## Examples

```bash
chains list evm                   # every registered EVM chain
chains info matic --json          # canonical metadata for a machine
chains resolve btc                # bitcoin
chains validate eth 0x1f9840a85d5aF5bf1D1762F925BDADdC4201F984
chains validate btc 4a5e1e4baab89f3a32518a88c31bc87f618f76673e2cc77ab2127b7afdeda33b --txid
chains identify 0x1f9840a85d5aF5bf1D1762F925BDADdC4201F984   # which chains accept this format
chains list --json | jq -r '.chains[] | select(.type == "utxo") | .key'
```

`chain` is anything [getChain](/guide/registry) accepts: `matic`, `btc`, `Arbitrum One`. Families for `list` are the eleven `type` values: `evm`, `utxo`, `solana`, `stellar`, `xrpl`, `move`, `ton`, `tron`, `octra`, `arweave`, `monero`.

## Exit codes

`info`, `resolve`, `validate`, `txid` and `list` exit 1 when they fail. The reason goes to stderr. Unknown chain, unknown family, an address or txid that doesn't fit, a chain with no txid check.

Why does a rejected address fail here and not in the tools? For a model it's an answer. For a shell script it's a failure, and `&&` deserves to know. `identify` exits 0 even when nothing matches. "No chain takes this" is an answer too.

```bash
chains validate btc bc1qw508d6qejxtdg4y5r3zarvary0c5xw7kv8f3t4 && echo fits
chains validate btc bc1qw508d6qejxtdg4y5r3zarvary0c5xw7kv8f3t5 || echo nope
```

```text
Invalid Bitcoin (bitcoin) address: "bc1qw508d6qejxtdg4y5r3zarvary0c5xw7kv8f3t5" - the Bech32 checksum does not hold, so a character is wrong
nope
```

A command line the CLI can't read fails before anything runs. That's a missing argument (`chains info` alone), a flag no command takes, or a value past the tool's length limit. The message names the problem, the exit code is 1.

A rejected address or txid comes back quoted. A newline or a terminal escape inside one can't forge a line under the error. Whitespace around it is trimmed first, like in the agent tools. An address copied out of a log keeps its trailing newline. One invisible byte shouldn't turn a good address bad.
