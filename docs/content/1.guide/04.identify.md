## The call

```ts
import { identify } from "@agntn/chains";

const { matches, unchecked } = identify("EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v");
matches.map((chain) => chain.key); // ["solana"]
unchecked; // []

identify("0x1f9840a85d5aF5bf1D1762F925BDADdC4201F984").matches.length; // 14, every EVM chain
identify("0x1").matches.map((chain) => chain.key); // ["aptos", "sui"]
```

`identify(address)` partitions the registry: `matches` holds every chain whose `assertAddress` accepted the string, `unchecked` holds every chain that carries no validator and so couldn't be asked. Only `InvalidAddressError` counts as a miss. Anything else a validator throws is a bug and comes back out.

## What a match means

Format only. Every EVM chain shares one format, so a `0x` address with 40 hex digits matches all fourteen, and that's the honest answer. A match narrows the family rather than naming the chain an address is used on. Same for `0x1` on Aptos and Sui: both write the framework address that way, and nothing in the string can tell them apart.

A miss on a chain says the string doesn't fit that format. A miss everywhere says no registered format fits, which isn't the same as the address being wrong. It could be a chain this package doesn't know.

## A grammar that fits everything

[NEAR](/chains/near) accepts a lot of lowercase names. Account IDs are 2 to 64 characters. They use `a-z`, `0-9`, and single `-`, `_`, or `.` separators.

That makes `bc1qw508d6qejxtdg4y5r3zarvary0c5xw7kv8f3t4` a valid NEAR account ID. So is `nope`. Does this Bitcoin address need a second owner?

`identify` reports chains whose validators accept an address. But acceptance alone doesn't mean a chain claims it. The `Chain` method `claimsAddress` can decline it for `identify`. By default, it says yes.

NEAR claims names with a dot and its typed forms. Those are 64 hex digits, `0x` plus 40 hex digits, `0s…`, and `0u…`. Bare words stay out of `identify`. This is a sensible limit. `assertAddress` still accepts them, so `getChain("near").assertAddress("aurora")` passes.

A lowercase `0x` address with 40 hex digits matches EVM chains and NEAR. It's an ETH-implicit account on NEAR, using the same 20 bytes.

## Unchecked isn't no

A chain without a validator is named as unchecked rather than skipped, because a silent skip would let "matches none" read as "belongs to no registered chain". The list is empty right now, every built-in chain validates, but a [custom chain](/guide/custom) that skips `assertAddress` lands there.

## On the CLI and in the tools

```bash
chains identify 0x1f9840a85d5aF5bf1D1762F925BDADdC4201F984
chains identify EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v --json
```

`identify` exits 0 even when nothing matches, because that's an answer too. It prints what `chains_address_identify` hands a model, word for word: the matches grouped by family, with the reach of a match spelled out. `--json` gives `{ address, matches, unchecked }`, the last two as arrays of keys.

```text
"0x1f9840a85d5aF5bf1D1762F925BDADdC4201F984" matches 14 of 38 checked chains.
evm (14): ethereum, base, arbitrum, optimism, polygon, bsc, avalanche, fantom, gnosis, linea, zksync, scroll, berachain, arc
A format match narrows the family; it does not prove the address is used on any of these chains.
```

The [Playground](/playground?op=identify) runs the same partition in your browser and lights up the families as you type.
